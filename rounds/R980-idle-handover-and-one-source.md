# R980 · 空闲逻辑接管 · 名单为唯一依据 · 目标循环的真根因

## 排班

1. 开发者三条反馈：①静默 10 秒要「换成空闲时的运行逻辑」，不是自写一个闲逛点；
   ②面板就是唯一依据——自动识别只认绿框里的矿物，剩下的旧路径删掉；
   ③她为什么接近不了那块矿，收放一次就好了？
2. 定位 ③ 的真根因（不是挡路块）：旧目标在缓存里被反复选中的死循环
   ——实例日志 00:34:54~00:35:31 每 ~2.5 秒一条 `目标跑出检索半径→清空` 轮回同一块。
3. 三件一起改：①删自写闲逛（让 TLM 空闲逻辑接管）；②删标签自动识别 + `!id` 拉黑（名单唯一）；
   ③缓存/扫描与「她到方块」半径口径统一 + 发现超出半径就弃框重扫。
4. 编译 / 护栏 / 打包 / 部署 / 回归 / 文档台账。

## 需求 / 来源

- ①「我不是说换成空闲时的运行逻辑吗？你直接照办不就好了？为什么还要整成这个样子？」
- ②「我要的效果是那个面板就是一个切实有效的面板，自动识别只会把绿色框里面的矿物识别为有效矿物，
  剩下的一律不识别为矿物。…剩下的是不是都是老版本的参与呢？是的话就删掉。」
- ③「女仆手上的工具可以挖掘任何方块。背包中的方块数量也是充足的。那么女仆为什么没能接近那个方块？
  我在发现这个问题之后，重新收放在同一个位置就可以执行了？」
- 并指出：上一轮的卡死看门狗「更加适合于女仆手上有工具、但遇到了一些无法破坏的方块」那类情况
  ——本轮保留并按此定位。

## 改法

### ① 静默窗口：删掉自写的闲逛，让 TLM 空闲逻辑自己接管

上一轮在静默窗口里另写了一个闲逛点（每 40 拍一换、点还常常离她不到一格），它会：

- **抢 TLM 的跟随目标**：主人正带她走、或 TLM 自己的走路逻辑正在驱动她时，往 `WALK_TARGET` 写点
  会把跟随目标顶掉 —— 实机看到的就是“只跟主人两秒就不跟了”（第一次写点正好在窗口开始后 2 秒）；
- **走一步停一步**：点太近→一步就到→到了就算完成、TLM 不再驱动她→站住，等下一个同样近的点。

现在静默窗口和「框空」两处都**不再由本模组写任何走位点**：清目标 → 停自己的导航 →
`setChainDrive(false)` 交回走位权 → return。这 10 秒她走的完全是 TLM 空闲那一套（跟随主人 / 自己溜达）。
`MaidWorkBehavior.idleWander` 及其字段（`wanderSpot` / `wanderAt` / `idleWanderCooldown`）一并删除。

### ② 名单为唯一依据：删标签自动识别与 `!id` 拉黑

删掉三条旧入口（两树，挖矿与伐木同口径）：

| 旧入口 | 原作用 | 现在 |
|---|---|---|
| 内置矿表 / 内置木材表（`reloadBuiltinOres` / `reloadBuiltinWoods`） | 配置加载前的占位表 | 删；`oreValueOf` / `woodValueOf` 首次调用时懒加载配置（表 = 名单） |
| 标签自动识别（`mine.tagAuto` / `wood.tagAuto`） | 带 `forge:ores`/`c:ores`、`#logs`/`#bamboo_blocks` 标签的方块自动算矿/算木材 | 删（含配置项、面板行、4 份语言、排班探测里的分支） |
| `!id` 拉黑行（`ORE_EXCLUDED` / `WOOD_EXCLUDED`） | “叉掉过”的方块永不算矿，连 tag 也翻不了案 | 删；小叉 = 从名单里去掉这一行（名单不认它 = 不挖/不砍） |

- `isTargetOre` / `isTargetWood` 判据不变（仍是名单），但背后只剩名单一条；排班探测里“名单空 + tag 关 = 无法判定放行”
  改为“名单空 = 任务不可用”（名单空她确实什么都不挖）。
- 面板网格只剩两态（绿框✓ / 空白）；列表里的旧 `!id` 行仍能看见、点「删除」清掉（历史存档兼容）。
- 配置校验器**仍接受** `!id` 行（若直接拒绝，老存档的整份配置会校验失败），解析时跳过 = 不进表 = 不挖，行为与旧版一致。

### ③ 原地不动的真根因：缓存的「框」与「她到方块」半径口径不一致

实例日志（NeoForge 实例，00:33:18开始正常挖矿；00:34:54 起突变）：

```
00:34:54.424  work exit: ... reason=mine 目标跑出检索半径→清空 detail=target=BlockPos{x=-1523, y=113, z=-793}
00:34:57.773  work exit: ... reason=mine 扫描节流(等5拍) detail=cooldown=4
00:34:59.523  work exit: ... reason=mine 目标跑出检索半径→清空 detail=target=BlockPos{x=-1523, y=113, z=-793}
   ... 同一块、同一行，每 ~2.5 秒一次，一直到 00:35:30
00:35:31.964  [promaid/离场] 大正女仆酒狐 离开世界（id 1265，reason=DISCARDED）   ← 玩家收放一次
00:35:33.354  [新实体 id 2876] —— 收放后立即正常挖矿
```

根因链：

1. `findOre` 优先走**缓存轮**（`ORE_CACHE`）；缓存的候选是按**锚点**算框的（`pickFromCache` 里 `|dx|>radius`）；
2. 她一路往下挖（y 103→88），锚点却还在旧位置——缓存里那块 `x=-1523,y=113,z=-793` 在锚点框内、却已在**她自己**的检索半径外；
3. 外层判据 `targetOutOfRadius(maid, target, radius)`（**她→方块**）把它清掉、`return`，但**没动缓存**；
4. 下一轮缓存又把同一块选回来 → 再被清掉 → **死循环**：不走路、不挖、不气泡（`WorkStatusReporter`
   在这条路上拿不到说法），也没有恢复通道。
5. 收放一次 = 新实体 = **空缓存** → 下一次全量扫描以她当前位置为锚点 → 立刻正常。这正是开发者观察到的
   “重新收放在同一个位置就可以执行”——与工具/方块数量**毫无关系**。

改法：

- `pickFromCache`（两树）加**她→方块**同口径过滤：在她自己半径外的缓存格**不参与本轮选择**；
- `fullScanOres` / `fullScanWoods` 的最优选择同步加这一条（仍记进 `found`，缓存保持完整：她走近后下一轮自然放行）；
- 外层「目标跑出检索半径」分支限只清目标不够——现在调 `dropStaleScan`：
  **废掉缓存 + 废掉分帧游标 + 把扫描框挪到她自己脚下**，下一轮从她当前位置重新判定“这一片有没有矿”。
- 实例日志也修正了一条旧误判：上一轮我把“00:34:49~00:35:33 没有日志”当成断开的 44 秒——实际那段时间里
  `目标跑出检索半径→清空` + `扫描节流` 两行一直在刷，只是被我当时的筛选器漏掉了。

### ④ 卡死看门狗（保留，按开发者口径定位）

上一轮加的静默看门狗（同一目标 + 没挪窝 + 进度不动满 8 秒 → 放弃当前块、记 30 秒“暂时够不到”、
清走位、气泡说一声、留痕日志）**保留**；它对本次这个循环本来就不会触发
（循环里 `targetPos` 每拍被置空，“同一目标”条件不成立）——它负责的是开发者点名的另一类：
**工具齐全、却撞上挖不动的方块**（基岩这类）时脱身并播报。

## 验收

- 挖空 / 砍空后说完提醒，她这 10 秒里跟着主人走 / 自己溜达，不再“跟两秒就不跟”、不再一步一停。
- 面板上绿框之外的方块（包括带矿物标签的模组矿）她一律不挖；加进名单后立刻开挖。
- 她不再出现“原地站着、不报错、不恢复”；真撞上挖不动的方块，八秒内放弃当前块并提醒一句。

## 边界

- **行为变化（重要）**：以前靠标签白捡的模组矿物 / 模组原木现在**不会自动挖/砍**，必须在面板里加进名单；
  已在名单里的（默认那批原版矿与原木）一字不变。
- 静默窗口内她跟随主人时**会跟出工作圈**（那就是 TLM 空闲逻辑的原样）——这是本轮刻意的。
- 历史存档里的 `!id` 行照旧能加载（跳过 = 不挖），在列表子页里可以点「删除」清掉；新版不再产生这种行。
- 名单全清空 = 她不挖 / 不砍（这是玩家的主动选择，排班也会把对应任务判为不可用）。
