## 定位与改法

### ① 固定翼降落：速度从未被压下来（设计值 0.80 ≠ 实机 2.8~3.2）

**定位**（两树，`MaidMountCompat`）：整条降落链路的水平速度由 `aircraftGovernSpeed(mount, AIRCRAFT_CRUISE_SPEED)` 管，而它是**"只压不拉 + 每拍最多削 0.04"**（`cap = max(target, hs − AIRCRAFT_SPEED_DECEL)`，`AIRCRAFT_SPEED_DECEL = 0.04`）。实机里 `推力=3.00`（引擎的冲刺推力）每拍给的速度增量**大于 0.04**，于是这个环永远追不上——`水平速度` 一路卡在 2.8~3.2（设计值 0.80 形同虚设）。而固定翼的**转弯半径 `r ≈ v/0.0298`** 随 v 线性变大（780 的推导）：v≈3 时半径 ≈100 格，她根本**转不进** `AIRCRAFT_LAND_CORRIDOR`（14 格）宽的进近走廊，只能一圈圈往外飞；`距接地点` 一过 `AIRCRAFT_LAND_PLAN_KEEP_D`（268）就判"漂太远"、作废重规划，方向又按她当时机头重挑 → 每拍换向 → 越飞越远 → 脱离降落档飞走。**第一次能落下来是运气**（恰好没飞出去）。

**改法**（两树，同一份逻辑；只在**降落链路**加一道硬限速，巡航/跟随档一个字不动）：

- **新增常量 `AIRCRAFT_LAND_SPEED_STEP = 0.15`**（格/拍）：降落链路每拍允许的减速量。0.15 > 引擎每拍给的增量（0.04 那个量级的削量压不住它），于是每拍把速度**真的**钳回落；又远小于"一拍急停"。
- **新增 `aircraftGovernSpeedHard(mount, target, step)`**：与 `aircraftGovernSpeed` 同形（`cap = max(target, hs − step)`、超了就按比例缩 `deltaMovement`），只把减速量换成 `step`。
- **降落链路四处接上**（`aircraftLandFinal` 的进场 / 进近、`holdAircraftPattern` 盘旋、`aircraftFlyToCircle` 进圈）：
  - **进场 / 盘旋 / 进圈**：一律 `aircraftGovernSpeedHard(mount, AIRCRAFT_CRUISE_SPEED, AIRCRAFT_LAND_SPEED_STEP)`——先让她**真能转到 0.80**（半径 ≈27 格），才可能对正走廊；
  - **进近段**：目标速度改成**随距离收敛到 0 的斜坡**
    `landSpeedCap = AIRCRAFT_CRUISE_SPEED × clamp(max(before,0) / AIRCRAFT_LAND_GLIDE_MAX_D, 0, 1)`
    （`before` = 到接地点的距离，`AIRCRAFT_LAND_GLIDE_MAX_D = 90`）——离接地点 90 格外 0.80、45 格外 0.40、到接地点正好 **0**。这就是开发者点名的**"让速度逐渐降为零"**；接地段照旧 `killHorizontal(FLARE_RETAIN=0.88)` 把最后一截收掉。
- **留痕**：`固定翼降落·进近` 那行日志新增 `限速=` 读数（写 `landSpeedCap`），下一轮"速度有没有一路降下去"一眼可读。
- **没动**：`aircraftGovernSpeed`（巡航档专用）、`aircraftCruise`（巡航/跟随档）、条带选址、`PLAN_KEEP_*`、下滑道、接地段高度闸、`killHorizontal`。

### ② 挖矿：「朝挡路块推进」那条路漏了"挖开头顶"（搭不上就永远卡住）

**取证**（同一次会话，`logs/latest.log` 13:32:07~13:32:22）：

```
13:32:07 work exit: … reason=mine 朝挡路块推进(够不着矿) blocker=BlockPos{x=-1407,y=24,z=-681} target=BlockPos{x=-1405,y=25,z=-680}
13:32:07 work walk stuck: … target=BlockPos{x=-1405,y=25,z=-680} stand=BlockPos{x=-1407,y=23,z=-681} feet=BlockPos{x=-1409,y=21,z=-683} dist=3 path=false -> stop+retarget
13:32:12 work exit: … reason=mine 朝挡路块推进(够不着矿) blocker=(-1407,24,-681) target=(-1405,25,-680)     ← 5 秒后一模一样
13:32:12 work walk stuck: … feet=(-1409,21,-683) dist=3 path=false -> stop+retarget
13:32:17 …（同样两行）
13:32:22 …（同样两行）
13:32:23 大正女仆酒狐 复活后补包已登记（收放救回）
```

脚下高度 `y=21` 整整 15 秒不动；挡路块在她**上方 3 格**（`y=24`），`path=false`（无路）；期间**零破坏**。

**定位**（`MaidMineBehavior`，两树）：「够不着挡路块 → 朝它推进」这条分支的次序是——挡路块在上方就试 `pillarUpStep` 搭高；搭不上（返回 false）就 `walkToBlockFace` 走过去。可 `walkToBlockFace` 的目标是**挡路块脚下那一格**（比她高 2 格），**走着够不到** → `path=false` 永远为真；`pillarUpStep` 又因为"头顶那两格是实心方块、垫不上去"而失败。**问题**：九百三十二 给 `approachOre` 的 `dy>=1` 分支补了 `digUpCap`（垫不上去就先**挖开头顶**），但**这条挡路块路漏了**——于是她够不着、搭不上、又不挖头顶，只能一遍遍 `stop+retarget`，直到玩家收放（重新召唤）才恢复正常。这正是开发者说的"有概率会被卡住、原因未知"。

**改法**（两树，`MaidMineBehavior`）：挡路块在她上方、`pillarUpStep` 失败后，**再试一次 `digUpCap`**（挖开正上方那块可挖方块给它让路；挖开后下一次 `pillarUpStep` 就有落脚点了）。日志沿用 `digUpCap` 自带的 `mine 头顶压住挖开`，所以"她卡住时到底在干嘛"日志里能看见。
